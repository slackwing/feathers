Deploy

Static files ship via one shell alias defined on the developer laptop:

ws_prod   →   website_sync . . master
          →   rsync -avz --delete  ./  acheong87@35.243.192.242:/var/www/html/
  • Requires master branch and a html/ cwd.
  • Protects .staging/, shared/assets/, and **/wordpress/ from --delete.
  • Exit 23 with Permission denied on .well-known/ssl-manager/* is expected — those are owned by the ACME/SSL manager on the VM. Site content still uploads.
  • No CI. Deploys are manual and diffable (git log) after the fact.

The Go backend (hobby-server) deploys separately via install.sh in its own repo. It rebuilds a Docker image, runs Liquibase against Cloud SQL to apply any new schema changes, then restarts the container.

Backend: hobby-server

One Go binary hosts multiple isolated projects. The rv project is one of them. Each project gets its own URL prefix, cookie scope, and (optionally) DB — all share this one hobby_server database for now.

The itinerary lives in two places:

  • assets/itinerary.json — the static "planned" itinerary. Immutable at read time.
  • itinerary_override in the DB — per-day overrides. Loaded and layered on top at render.

location_user holds two flavors keyed by the same primary key:

  • kind='override' — patches a row in the static catalog (map-sources.json → map.json). Any non-null column wins over the catalog. Soft-delete via deleted_at hides the location without losing the override — useful for "don't show this one, but remember I edited it."
  • kind='new' — brand-new user-added location. Same columns; catalog has nothing to fall back to.

Route map (SVG)

The map on the itinerary page is a hand-drawn SVG spline that traces the trip in one continuous stroke. It reads from three JSON files:

  • map-sources.json — source of truth for locations (majors + sleeps + POIs) and the route sequence.
  • map.json — computed output: same locations + Google Directions distances/times between them + Open-Meteo weather for the day each sleep spot is expected. Regenerated by scripts/compute_everything.py. Both APIs are cached on disk in .cache/ (gitignored).
  • trip.json — the day-level content model (facts, activities, sleep IDs). See assets/META.md for the provenance schema.

Rendering

map-v2.js reads map.json, computes each location's normalized "route fraction" (0.0 at San Diego → 1.0 at NYC), places it along the spline, and draws:

  • Majors — city labels at their point on the route.
  • Sleeps — 🚐 emojis with a color-graded temperature dot (historical + forecast, °C/°F toggle top-right).
  • POIs (Points Of Interest) — small emoji dots off the route, hoverable for a name pop.
  • An animated "here we are now" marker as the trip progresses.

Editing (auth)

Signed-in users can click a location to override its name, coords, sleep-type, or emoji — those edits go into location_user as kind='override' rows. New locations added via the map get kind='new' rows. Everyone else sees the layered result.

Admin

admin.html is the auth-gated dashboard. Public visitors see the login modal.

Currently hosts:

  • 🍩 Dunkin' bet participants — add/remove bettors, edit their guess and dot color. Backed by the dunkin_participant table via /rv/api/dunkin/participants. New rows land at sort_order = (max + 10).

Editing on the main site (day cards, locations, prep items, notes) is not on admin.html — it's inline on each page, gated by the same rv_session cookie.

Auth

Everything is one cookie: rv_session, Path=/rv/, HttpOnly, Secure, SameSite=Lax. The Go server checks it on every write; reads are public unless noted. Bcrypt on the password hash, cost 12. There's no OAuth, no email flow, no 2FA — users are created by INSERT.

Dunkin' Donuts forecast

Some bettors guessed how many Dunkins we'd see across the trip. The chart plots each real sighting as a line segment, marks the current point with 🍩, and forecasts the trip-end count with three curves — linear, rolling rate + tapering accel, and a flat "if we see none more" reference line. Shaded band spans the pessimistic and optimistic curves.

The formula

All fitting happens in the browser off dunkin_log rows. Model:

count(d) = c₀ + rate·(d − d₀) + ½·accel·(d − d₀)²

Anchored at the last logged sighting (d₀, c₀). Anchoring at NOW made the projection collapse as "now" slid forward. Instead we freeze the anchor and let a phantom point at u_now = now − d₀, y = 0 encode "still no new sighting" — pulls the fit toward flat as time passes.

Least-squares fit on the last 20 logs, each log weighted exp(−|u|/FIT_TAU) so recent points dominate and older ones fade smoothly. The phantom carries a small fixed weight so a long gap nudges rather than yanks the fit. Then accel tapers with an exponential decay of its own so a burst doesn't compound forever:

accel(u) = accel · exp(−u/τ)
rate(u) = rate + accel·τ·(1 − exp(−u/τ))
count(u) = c₀ + rate·u + accel·τ·(u − τ·(1 − exp(−u/τ)))

A monotonic guard clips count at the moment the local rate would cross zero — no un-seeing donuts.

Constants

KnobValueEffect
RECENT_WINDOW20Max real logs in the fit. Time-weighting does most of the shaping; this is a soft cap.
FIT_TAU1.0 dSensitivity knob. Smaller = a recent cluster dominates; larger = slower to react.
PHANTOM_W0.05Weight of the "no sighting yet" phantom relative to a real log at the anchor.
TAPER_MULT, TAPER_TAU_MIN/MAX4.0 × window span, clamped 2–14 dHalf-life of the accel taper. Determines how long a burst keeps bending the curve up.
MIN_LOGS_FOR_PROJECTION5No forecast lines until we have enough data to say something meaningful.
